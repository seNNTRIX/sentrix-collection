# 졸업전시

맥북에서 [실험실](http://127.0.0.1:5190/)을 열고, 큰 모니터에서 [SentriX 개요](http://127.0.0.1:5190/display#B1-Overview)를 연다. 두 번째 주소는 제품 대시보드의 빌드 파일을 그대로 제공한다. 개요에서 자동 감지 기록을 누르면 서비스 호출 관계, 후보 순위와 근거를 조사할 수 있다.

- 관람객 화면은 실시간 장애 주입을 사용한다. CPU 포화와 Pod 중단은 서비스 11개에서 선택한다. 네트워크 지연과 패킷 손실은 호출 방향이 정의된 경로 15개에서 선택한다. 재현 파일 유무는 선택 조건에 들어가지 않는다.
- 개요에서 평상시 요청량·오류율·지연을 1분 확인한 뒤 장애 실험실에서 대상과 유형을 골라 **장애 주입**을 누른다. Chaos Mesh가 실험을 적용하면 주입 시각이 표시된다. 실험에 설정한 지속 시간은 180초다. 화면의 복구 시각은 클러스터가 실제로 복구를 확인한 시각이다. 장애 주입의 복구와 모델의 정상 판정은 서로 다른 시각일 수 있다.
- 큰 모니터는 같은 운영 환경을 계속 관측한다. Java가 30초 구간마다 Python 모델을 호출하고 그 결과로 장애 기록과 후보를 저장한다. 모델이 판정을 보류하거나 대상을 맞히지 못한 경우에도 반환값을 그대로 보여준다.
- 보관한 실험 기록과 전시용 재분석 도구는 별도로 남아 있다. 관람객 화면은 이를 사용하지 않는다.

## 실행

기존 쇼핑몰, MySQL, 지표 수집기, Java(8080)와 Python 모델(8000)을 실행한다. 맥북에서는 **맥북 전시 시작.command**로 운영 환경을 준비하고 **관람객 두 화면 시작.command**로 실험실과 제품 개요를 연다. 저장된 실험 전용 서버(8081·8001)는 필요하지 않다. 주입에는 로컬 전시 클러스터의 Chaos Mesh와 operator-rbac.yaml의 전용 계정 권한이 필요하다.

검증 명령은 `python3 -m unittest discover -s exhibition`이다.

## 맥북 실측 · 2026-11-24

첫 실행에서 상품 조회 경로에 지연이 적용된 시각은 01:09:18, 복구 확인은 01:14:45 KST였다. 주입 전에도 모델은 이상을 반환했다. 주입 구간에는 관측 조회 시간 초과와 지표 표본 부족으로 원인 후보가 나오지 않았다. 복구 시점 기준 직전 6분의 컨테이너 지표 수집 성공률은 33%였다. 전시용 Prometheus 수집 주기와 제한을 3초에서 5초로 조정했다.

두 번째 실행은 지표 확인을 마쳤지만 주입 요청 접수를 확인하지 못했다. 당시 Chaos Mesh 제어기는 Kubernetes의 제어권 갱신 시간을 넘겨 재시작했다. 이 맥의 단일 제어기에서 CPU 상한을 750m로, Helm의 `controllerManager.leaderElection` 아래 `leaseDuration`, `renewDeadline`, `retryPeriod`를 각각 60초·40초·5초로 조정했다. 주입 요청 응답이 끊기면 콘솔은 같은 실험 ID로 접수 여부를 다시 읽는다.
