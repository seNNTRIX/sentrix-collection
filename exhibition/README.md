# 졸업전시

시드니 전시는 맥북에서 [실험실](http://127.0.0.1:5191/)과 [대시보드](http://127.0.0.1:5191/display#B1-Overview)를 연다. 5190은 맥북 로컬 클러스터 전용이다. 전시 실행 스크립트는 시드니 연결이 열려 있으면 5191을 먼저 연다. 주입 중에는 버튼에 잔여 시간이 표시되고, 주입이 끝나면 마지막 분석 결과를 확인할 때까지 다음 실험을 기다린다.

- 관람객 화면은 실시간 장애 주입을 사용한다. CPU 포화와 Pod 중단은 서버 요청 지표가 확인된 전시 서비스 7개에서 선택한다. 네트워크 지연과 패킷 손실은 이 서비스들 사이에 호출 방향이 정의된 경로 9개에서 선택한다. 재현 파일 유무는 선택 조건에 들어가지 않는다.
- 개요에서 평상시 요청량·오류율·지연을 1분 확인한 뒤 장애 실험실에서 대상과 유형을 골라 **장애 주입**을 누른다. Chaos Mesh가 실험을 적용하면 주입 시각이 표시된다. 실험에 설정한 지속 시간은 180초다. 화면의 복구 시각은 클러스터가 실제로 복구를 확인한 시각이다. 장애 주입의 복구와 모델의 정상 판정은 서로 다른 시각일 수 있다.
- 큰 모니터는 같은 운영 환경을 계속 관측한다. Java가 30초 구간마다 Python 모델을 호출하고 그 결과로 장애 기록과 후보를 저장한다. 모델이 판정을 보류하거나 대상을 맞히지 못한 경우에도 반환값을 그대로 보여준다.
- 보관한 실험 기록과 전시용 재분석 도구는 별도로 남아 있다. 관람객 화면은 이를 사용하지 않는다.

## 실행

기존 쇼핑몰, MySQL, 지표 수집기, Java(8080)와 Python 모델(8000)을 실행한다. 맥북에서는 **맥북 전시 시작.command**로 운영 환경을 준비하고 **관람객 두 화면 시작.command**로 실험실과 제품 개요를 연다. 저장된 실험 전용 서버(8081·8001)는 필요하지 않다. 주입에는 로컬 전시 클러스터의 Chaos Mesh와 operator-rbac.yaml의 전용 계정 권한이 필요하다.

검증 명령은 `python3 -m unittest discover -s exhibition`이다.

## 맥북 실측 · 2026-11-24

첫 실행에서 상품 조회 경로에 지연이 적용된 시각은 01:09:18, 복구 확인은 01:14:45 KST였다. 주입 전에도 모델은 이상을 반환했다. 주입 구간에는 관측 조회 시간 초과와 지표 표본 부족으로 원인 후보가 나오지 않았다. 복구 시점 기준 직전 6분의 컨테이너 지표 수집 성공률은 33%였다. 전시용 Prometheus 수집 주기와 제한을 3초에서 5초로 조정했다.

두 번째 실행은 지표 확인을 마쳤지만 주입 요청 접수를 확인하지 못했다. 당시 Chaos Mesh 제어기는 Kubernetes의 제어권 갱신 시간을 넘겨 재시작했다. 이 맥의 단일 제어기에서 CPU 상한을 750m로, Helm의 `controllerManager.leaderElection` 아래 `leaseDuration`, `renewDeadline`, `retryPeriod`를 각각 60초·40초·5초로 조정했다. 주입 요청 응답이 끊기면 콘솔은 같은 실험 ID로 접수 여부를 다시 읽는다.

## Linux 전시 서버에서 연결하기

큰 모니터에는 기존 제품의 `/display#B1-Overview`를, 관람객 조작용 맥북에는 같은 주소의 `/`를 연다. 시드니 전시는 맥북의 5191번을 SSH로 서버의 127.0.0.1:5191에 연결한다. 기본 로컬 전시 포트는 5190이다. DB·모델·주입 API는 외부에 공개할 필요가 없다.

- 전시 서버는 `SENTRIX_EXHIBIT_PORT=5191`과 `SENTRIX_EXHIBIT_SERVICE_KUBECONFIG`로 실행한다. 후자는 `operator-rbac.yaml`의 전시 계정을 사용하는 kubeconfig 경로다. 서버에서 만료되기 전에 단기 토큰을 갱신한다.
- 정상 트래픽에서 11개 쇼핑몰 서비스 가용성, 구매 완료, 지표 수집 성공을 먼저 확인한다. CPU·메모리 표본이 모자라면 kubelet 측정 간격과 Prometheus의 cAdvisor 수집 간격을 각각 확인한다. 시드니에서는 두 간격을 2초로 설정했고, 모델은 기존대로 5초 격자의 관측값으로 30초를 분석한다.
- 고정된 모델로 5분의 정상 기준 데이터를 저장하고 이후 별도 10분의 정상 구간에서 탐지 점수의 95백분위수를 계산한다. 장애 실험은 기준값을 저장하고 자동 분석을 켠 뒤 시작한다. 시드니에서는 10초 간격으로 끝나는 30초 구간 두 개가 연속으로 기준을 넘고 관측 지표에도 이상이 나타나야 경보를 연다. 상세 조건은 모델 서버 README의 ‘실시간 환경의 경보 확인’에 기록했다.
- 시연 결과는 주입 전 모델 판정, 클러스터의 장애 적용·복구 시각, 적용 중 최초 이상 판정, 선택한 서비스 또는 경로의 실제 순위, 복구 후 장애 기록 상태를 함께 확인한다. 경로 지연을 측정해도 모델의 이상 판정이나 1순위 적중이 보장되지는 않는다.

### 시드니 경로 지연 실측 · 2026-11-24 (KST)

실험 대상은 `frontend → productcatalogservice`였다. 최초 Pod 주소만 지정한 실험에서는 제어기가 주입을 확인했지만 호출자 쪽 trace p90은 주입 전 0.31ms, 주입 중 0.29ms였다. 이 시도에서는 대상 경로가 원인 후보에 들지 않았다. 소스 Pod의 송신 경로에서 서비스 가상 IP도 일치하도록, 선택 목록에서 검증한 도착 서비스의 클러스터 DNS 이름을 포함했다. 훈련 모델과 경보 기준은 그대로 유지했다.

수정 후 03:05:02에 지연을 주입하고 03:08:02에 해제했다. 독립적으로 읽은 30초 trace 구간에서 대상 경로의 호출자 p90은 0.30ms → 200.31ms → 0.31ms였다. 주입 직전 자동 판정은 정상이었다. 03:06:04에 첫 이상 판정이 저장됐고 대상 경로가 1순위였다. 지연 주입 중 끝난 여섯 번의 30초 판정에서 같은 경로가 모두 1순위였다. 앞선 무주입 구간에도 이상 판정이 기록됐다. 이 단일 실험은 적중률이나 오탐률 평가가 아니다.

### 시드니 오탐 및 자동 종료 검증 · 2026-11-24 (KST)

정상 구매 300건이 모두 성공하고 11개 서비스가 가용했던 10분에서, 30초 분석 구간 58개의 점수 95백분위수(0.108681)를 계산했다. 이 값만 적용했을 때 이전 장애는 종료됐지만 새 오탐이 두 번 발생했다. 전시 환경에 한해 모델의 연속 이상 점수와 실측 증상(지연·오류·자원 사용률·요청량)을 함께 확인하도록 설정했다. 원인 후보 순위에는 관람객이 선택한 서비스나 주입 시각을 사용하지 않는다.

아래 시각은 장애 기록에 저장한 분석 구간의 종료 시각이다. 화면에는 분석·저장 후 표시된다. 지연 실험에서는 03:43:50에 주입이 해제됐고 03:44:30까지의 데이터를 정상으로 판정했다. 03:45:04에 저장된 결과가 열어 둔 장애 상세 화면에 자동으로 반영됐다.

| 실험 | 별도로 확인한 관측값 | 처음 감지했을 때의 후보 | 자동 종료 |
|---|---|---|---|
| frontend → productcatalogservice 지연 | 호출자 p90이 0.30 → 201.04 → 0.29ms | 대상 경로 1위. 주입 중 여섯 번 모두 1위 | 03:44:30 |
| productcatalogservice CPU 포화 | CPU 한도 대비 사용률 0.99 → 100.01 → 1.00% | 해당 서비스 1위 | 03:49:30 |
| paymentservice Pod 장애 | 가용 Pod 1 → 0 → 1. 30초당 성공 구매 15 → 0건, 기록 종료 직후 15/15건 성공 | 해당 서비스 2위, 다음 이상 구간에서 1위 | 03:56:00 |
| frontend → productcatalogservice 패킷 손실 2% (재시험) | 122개 드롭 관측. 호출자 p99가 0.62 → 205.40 → 1.22ms | 대상 경로 순위 4 → 1 → 4 → 4 → 4 | 04:13:30 |
| 트래픽 급증 | k6 구매 시도 30초당 15 → 45 → 15건 | 진입점 frontend 3위, 다음 이상 구간에서 1위. 외부 트래픽 증가는 단일 서비스 장애와 구분해 해석 | 04:05:30 |

트래픽 급증은 180초 동안 추가 k6 부하를 실행해 검증했다. 위 순위는 각 실험에서 관측한 위치 후보이며 다섯 장애 유형에 대한 분류 정확도를 뜻하지 않는다. 지연과 동시에 다른 실험이 시작된 한 차례의 기록은 표에서 제외했다.

첫 패킷 손실 실험에서는 p90이 거의 움직이지 않아 주입 도중 장애 기록이 두 번 닫혔다. 호출 표본이 충분한 경로에는 p99 확인을 추가했다. 같은 경로 재시험에서는 04:09:59에 손실을 적용하고 04:12:59에 해제했다. 장애 기록은 한 건으로 유지됐고 해제 후 자동 종료됐다.

별도로 수집한 정상 구간은 수정 전후 검증 회차별 각 5개였다. 두 회차 모두 오탐 0건이었고, 최종 코드로 첫 회차 5개를 다시 조회해도 모두 정상이었다. 지연·CPU·Pod·트래픽 실험의 최초 탐지와 종료 시점 8개도 최종 코드로 다시 조회해 같은 판정을 확인했다. 이 구간 수로 운영 전체의 오탐률을 추정할 수는 없다.

## 11월 24일 공개 대시보드와 순위 비교

공개 HTTPS는 `public-display.nginx.conf`를 적용한 읽기 전용 서버의 5192번 포트에 연결한다. 특정 환경의 지표, 장애 이력, 모델 판정, trace와 로그 건수를 공개한다. 원문 로그, 데이터 소스 주소, 변경 요청과 실험 제어는 운영자용 5191번 포트에서만 사용한다. 임시 터널을 다시 시작하면 공개 주소와 QR을 갱신해야 한다.

아래 결과는 시드니 전시 환경에서 비교한 첫 이상 경보의 정답 위치다. 양쪽에 동일한 30초 입력과 기존 판정 조건을 적용하고 순위 계산만 바꿨다.

| 실험 | 정답 위치 | 기존 | 호출 p99 반영 |
|---|---|---:|---:|
| 패킷 손실 2% | frontend → currencyservice | 4위 | 1위 |

세 번째 경로의 30초 표본은 약 60건으로 p99 증거에 요구하는 100건보다 적었다. 배포 후 frontend → currencyservice에 패킷 손실을 다시 주입했을 때 이상으로 저장된 6개 구간에서 모두 해당 경로가 1위였다. 실험은 04:39:06 KST에 종료됐고 사건은 04:39:30에 자동 종료됐다.

### 2026-11-24 패킷 손실 진단

시드니에서 06:09:47~06:12:47(KST) recommendationservice → productcatalogservice 경로에 2% 손실이 적용됐다. 복구 전 온전히 포함된 30초 분석 구간의 모델 판정은 정상이었다. 다섯 구간 각각에서 관측된 직접 호출은 60건으로 경로 p99의 최소 100건보다 적었다. 실험 구간의 호출 최대 지연은 208.85~418.57 ms, p90은 0.57~2.02 ms였다. 이 실험은 전시 환경의 미탐 사례다.

### 전시 실험실의 주입 조건과 실제 판정

방문자 화면은 서버의 고정 프로필에서 조건과 기본 대상을 읽는다. 같은 일곱 서비스와 아홉 직접 호출 경로에서 선택할 수 있다. 주입 전 최근 2분의 완료 판정이 정상인지 확인한다. 네 유형 모두 180초 후 해제하며 관측 데이터로 계산해 저장한 이상 판정과 주입 해제 상태를 따로 표시한다.

2026-11-24 시드니에서 기존 2% 손실로 놓쳤던 recommendationservice → productcatalogservice 경로를 15% 고정 손실로 재시험했다. 06:29:43 KST 주입 전 정상, 06:30:30 분석 구간 정상, 06:31:00 구간 이상(0.86178), 최초 경보에서 실제 경로 1위, 06:32:43 주입 해제를 확인했다. 새 조건으로 한 경로에서 수행한 단일 시험이다. 전시 화면의 원인 순위에는 주입 대상 정보를 전달하지 않는다.
