# R4b 결과 해석 (처음 보는 원인 서비스)

전체 표: `results.md`, 수치: `results.json`, 사전 등록: `config.yaml`(커밋 `70960a9`, 결과 전에 커밋).

## 1. 진단: feature로 서비스를 알아볼 수 있는가

| feature | 후보 | 서비스 맞히기 정확도 | 우연 수준 |
|---|---|---|---|
| core 35개 | 11개 | **0.986** | 0.091 |
| rel 18개(변화량만) | 11개 | 0.792 | 0.091 |
| rel 18개 | trace 있는 7개 | 0.926 | 0.143 |

- **core feature만 보고도 서비스를 거의 100% 알아본다.** 가설 1("얼굴 정보")을 뒷받침한다.
- **변화량만 남겨도 서비스를 꽤 알아본다.** trace가 있는 서비스는 변화량 패턴 자체가 서비스마다 다르다. 얼굴 정보가 줄었을 뿐 없어지지는 않았다.
- 이 진단은 "알아볼 수 있다"는 뜻이지 "모델이 그걸로 판단했다"는 증명은 아니다. 아래 2절 결과와 함께 해석한다.

## 2. 서비스 하나 빼기 (주 기준, 90 case)

| 방법 | AC@1 | Avg@5 (95% CI) | 통계 기준선 대비 (95% CI) | 판정 |
|---|---|---|---|---|
| 통계 기준선 stat_combined | 0.794 | 0.943 (0.916–0.967) | — | — |
| V1 core (R4 고정 후보) | 0.767 | 0.889 (0.833–0.933) | −0.054 (−0.100 ~ −0.012) | 나쁨 |
| V2 rel (변화량만) | 0.844 | 0.942 (0.907–0.971) | −0.001 | 차이 없음 |
| V3 rel + 단조 제약 | 0.856 | 0.951 (0.920–0.978) | +0.008 | 차이 없음 |
| **V4 rel과 통계 기준선 순위 평균** | **0.865** | **0.959 (0.933–0.979)** | **+0.016 (0.001 ~ 0.030)** | **나음** |

- **R4의 약점이 재현됐다.** 하이퍼파라미터를 중첩 LOSO로 골라도 core는 통계 기준선보다 나쁘다.
- **얼굴 정보를 빼면 약점이 대부분 사라진다.** rel은 core보다 +0.053(CI 0.022~0.089) 낫다. currency는 0.833에서 0.944로, productcatalog는 0.778에서 0.944로 오른다.
- **단조 제약은 rel 대비 차이가 없다**(+0.009, CI −0.011~0.031).
- **순위 평균(V4)만 통계 기준선보다 확실히 낫다.** 다만 신뢰구간 하한이 0.001이라 아슬아슬하다. V3과의 차이는 "차이 없음"이다.
- **장애 종류별:** 손실(loss)은 모든 방법이 약하다(0.75~0.85). 처음 보는 서비스의 손실 장애가 가장 어려운 경우다.

## 3. 반복 회차 CV (보조 조건)

| 방법 | Avg@5 | 통계 기준선 대비 |
|---|---|---|
| V1 core | 0.996 | 나음 (R4 값과 같음, 재현 확인) |
| V2 rel / V3 | 0.996 / 0.996 | 나음 |
| V4 순위 평균 | 0.981 | 나음 (+0.038) |

- **본 서비스에서는 얼굴 정보가 필요 없었다.** rel이 core와 같은 0.996이므로, 얼굴 정보는 일반화만 해쳤다.
- **V4는 본 서비스에서 대가가 있다.** 순수 LightGBM보다 0.015 낮다. 통계 기준선의 실수를 일부 물려받기 때문이다.

## 4. 사전 규칙에 따른 결정

- 우월 등급: LOSO에서 통계 기준선보다 낫고 반복 CV에서 나쁘지 않은 후보는 **V4 하나**다.
- **linux-v1 주 순위 방법: V4 = (rel 18개 feature LightGBM LambdaRank)와 stat_combined의 case 단위 순위 평균**

## 5. 해석과 한계

- 결론을 쉽게 말하면 이렇다.
  - 학습 모델이 "이 서비스는 원래 범인이 아니다"를 외우는 문제는 서비스를 알아보게 하는 feature를 빼면 대부분 해결된다.
  - 거기에 통계 방법을 섞으면, 처음 보는 서비스에서도 통계 방법보다 약간 낫다.
- V4의 우월은 아슬아슬하다(하한 0.001). 서비스당 18 case뿐이라, 다른 데이터에서도 V4가 V3보다 낫다는 보장은 없다.
- R4b는 R4 결과를 본 뒤 설계했다. 비교 대상을 4개로 제한했지만, 고른 V4의 LOSO 점수는 낙관적일 수 있다. 공정한 시험은 linux-v1이다.
- 결과를 본 뒤 바꾼 것: 없음. 실행은 한 번에 끝났다.

## 6. R5로 넘길 것

- **순위:** V4로 고정한다. 구성은 rel 18개, 30초 window, LambdaRank, stat_combined와의 순위 평균이다. 하이퍼파라미터 고정 규칙은 R5에서 정한다. LOSO 선택값은 num_leaves 7~15, 100~300 trees로 서비스마다 달랐다.
- **linux-v1 보고:** V4, rel 단독, stat_combined 세 가지를 모두 보고한다. paymentservice가 원인인 case는 따로 본다.
- **탐지:** 탐지 모델(R4)도 core feature를 쓴다. R5에서 탐지 feature도 rel 기준으로 맞출지 결정해야 한다. 이번 실험에서는 탐지를 비교하지 않았다.
