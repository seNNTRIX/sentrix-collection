# 사전 등록: 로그 의미 변화 특징이 원인 서비스 순위를 개선하는가 (R8)

작성일: 2026-11-16
상태: linux-v1 장애 구간 로그를 이 실험 목적으로 열기 전에 커밋한다.
데이터 번역 결정: `docs/LINUX-V1-DATA-TRANSLATION.md` (같은 커밋)
기준 방법: `docs/METHOD-FREEZE-v2.md` (고정 커밋 `399d3d0`). 이 실험은 고정 방법을 바꾸지 않는 **추가 실험**이다.

## 1. 질문과 가설

**질문:** 여러 서비스에 동시에 이상 증상이 나타날 때, 각 서비스의 평소 로그와 비교한 **로그 내용(의미) 변화**를 기존 원인 서비스 순위 모델(Random Forest rel18)에 더하면 원인 서비스 순위가 좋아지는가?

**가설:** 서비스마다 평소 남기는 로그가 다르므로, 같은 서비스의 평소 로그 대비 의미 거리를 평소 거리 분포로 보정한 특징(D)은 기존 특징만 쓴 경우(A)보다 원인 서비스 순위를 높인다.

**주장하지 않는 것**
- MiniLM이나 로그 임베딩 자체를 새로 만들었다고 주장하지 않는다.
- 이 설계가 원인과 전파 증상(호출한 서비스의 오류 로그)을 자동으로 구분한다고 주장하지 않는다. 이는 실험으로 확인한다.
- D가 B보다 좋아도 "의미를 이해했기 때문"이라고 단정하지 않는다. "이 실험에서는 MiniLM 표현이 문자 기반 표현보다 유리했다"고만 쓴다.
- 대표 로그를 화면에 보여 주는 것은 관측 근거 제공이며, 원인 순위 개선과는 별도로 보고한다.

## 4. 정상 기준과 의미 변화 특징

### 4.1 기준 구간

- 고정 방법의 `baseline_stats` 구간만 쓴다 (RE2-OB: 장애 −720 ~ −420초, linux-v1: warmup 끝(180초) ~ 장애 −120초). 장애 이후 로그, 다른 run(대조 run 포함)의 로그는 기준에 넣지 않는다. 장애 구간에서 기준을 갱신하지 않는다.
- 기준 구간을 **시각 기준으로 앞 절반 / 뒤 절반**으로 나눈다.
  - 앞 절반 = **비교 대상 로그 집합(R)**
  - 뒤 절반 = **정상 거리 분포** 계산용 window
- 뒤 절반 window에 들어간 로그는 R에 넣지 않는다(자기 자신과 비교 금지). 겹치는 window를 쓰더라도 앞·뒤 절반의 경계를 넘는 window는 뒤 절반 분포에서 뺀다.

### 4.2 거리

- 로그 하나의 거리 = `1 − max(cos(로그, r) for r in R)`
- window·서비스마다 두 값을 계산한다: 거리의 **평균**, 거리의 **90번째 백분위**
- window는 고정 방법과 같다 (30초 길이, 10초 간격, onset 정렬, 반열린 구간).

### 4.3 보정 (정규화)

- 각 값 x에 대해 `(x − 뒤 절반 window 값들의 중앙값) / 뒤 절반 window 값들의 IQR`
- IQR = 0이면 `x − 중앙값` (고정 방법 robust delta와 같은 규칙)
- **C와 D 모두** 같은 방식으로 보정한다.

### 4.4 유효성과 결측

- window 안 해당 서비스 로그가 `N_min`개 미만이면 그 window의 두 값은 NaN, 유효성 표시 `f_lsem_valid = 0`
- R의 로그가 `M_min`개 미만이거나 뒤 절반 window가 5개 미만이면 그 run·서비스 전체가 NaN, `f_lsem_valid = 0`
- **로그가 없다고 의미 변화가 크다고 처리하지 않는다.** Pod 장애의 로그 중단은 A′의 로그 개수 변화와 기존 결측 처리가 담당한다.
- RF 입력에서 NaN은 고정 방법과 같이 0(정상과 차이 없음)으로 바꾼다. 유효성 표시는 별도 열로 넣는다.

### 4.5 새 특징 (서비스·window 단위)

| 열 | 뜻 |
|---|---|
| `f_lsem_dmean` | 의미 거리 평균의 보정 변화량 |
| `f_lsem_dp90` | 의미 거리 90번째 백분위의 보정 변화량 |
| `f_lsem_valid` | 위 두 값을 계산할 수 있었는지 (1/0) |

B·C는 같은 이름에 접두어만 다르게 둔다 (`f_lchr_*`, `f_lsemall_*`).

## 5. 비교군 (같은 분할·같은 모델 설정·같은 평가 대상)

| 실험 | 원인 순위 모델 입력 | 확인하려는 것 |
|---|---|---|
| A | rel 18개 (고정 방법 그대로) | 현재 기준 성능 |
| A′ | A + `f_log_rate_lr`, `f_log_err_rate_d` (서비스 단위, 기존 정의) | 단순 로그 정보만으로 충분한가 |
| B | A′ + 문자 n-gram 해싱 거리 3개, 서비스별 R | 문자 패턴 변화가 도움이 되는가 |
| C | A′ + MiniLM 거리 3개, **전체 서비스** R (서비스별 R과 같은 개수로 무작위 추출, seed 20261116) | 서비스 구분 없이 비교한 효과 |
| D | A′ + MiniLM 거리 3개, **같은 서비스** R | 서비스별 정상 기준을 둔 효과 |

**표현 설정 (고정)**
- MiniLM: `sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`, 384차원, max_seq_length 256, 정규화된 벡터, 추가 학습 없음
- 문자 n-gram 해싱(B): scikit-learn `HashingVectorizer(analyzer="char_wb", ngram_range=(3,5), n_features=2**18, alternate_sign=False, norm="l2")`. 어휘 학습이 없어 장애 때 처음 나오는 단어도 표현된다. 해시 충돌이 있으며 TF-IDF와 같은 방법이 아니다.
- B·C·D는 전처리, 기준 구간, window, 거리 집계, 보정, 유효성 규칙이 모두 같고 **표현 방법과 R의 범위만** 다르다.
- linux-v1에는 rx/tx 패킷 신호가 없어 A의 rel 18개 중 4개가 항상 NaN(→ 0)이다(`docs/LINUX-V1-DATA-TRANSLATION.md` 1절). A~D 모두 같은 조건이다.

**모델 (고정)**
- scikit-learn 1.5.2 `RandomForestClassifier`, n_estimators 300, min_samples_leaf 100, max_features 0.5, random_state 0 (고정 방법과 같음)
- 행 = (window, 후보 서비스), 정답 서비스 = 1. 서비스 이름은 넣지 않는다.
- window 점수 = 원인일 확률, case 점수 = onset+60 ~ 300초 window 점수 평균 (고정 방법과 같음)

**학습 데이터 (A~D 동일)**
- 기본: RE2-OB 90 case + linux-v1 학습 fold의 적격 CPU·Pod case (고정 방법 B 방식과 같음)
- RE2-OB에서 로그 특징을 만들 수 없는 case·서비스는 NaN → 유효성 0으로 두고 같은 구성을 유지한다. 그 개수를 보고한다.
- RE2-OB 대부분에서 만들 수 없으면(6절 확인 결과), **A~D 모두 linux-v1 학습 fold만으로 학습**하고, 고정 방법의 A(혼합 학습) 성능은 참고값으로만 둔다.

## 6. RE2-OB에서 먼저 정하는 것 (linux-v1 보기 전)

**확인 (결과 전):** 90 case 모두 `message` 열이 있는지, 본문 형식, 주입 도구 로그 혼입, 기준 구간 앞·뒤 절반의 서비스별 로그 수.

**조정 가능한 값은 이것뿐이다:**

| 값 | 후보 | 고르는 기준 |
|---|---|---|
| `N_min` (window 최소 로그 수) | 3, 5, 10 | RE2-OB에서 D의 처음 보는 서비스 LOSO Avg@5 최대, 같으면 작은 값 |
| `M_min` (R 최소 로그 수) | 20, 50 | 같은 기준, 같으면 작은 값 |

- 위 두 값은 B·C·D에 똑같이 적용한다.
- 문자 n-gram 범위, 모델, 거리 집계, 보정 방식 등 나머지는 조정하지 않는다.
- RE2-OB에서 정한 값은 결과와 함께 이 문서 아래 "고정 기록"에 커밋한 뒤 linux-v1에 적용한다.
- RE2-OB의 A~D 결과는 **개발 결과**로 보고한다 (값을 고른 데이터이므로 낙관적).

## 7. linux-v1 평가

| 항목 | 값 |
|---|---|
| 분할 | 반복 회차 3-fold (r01·r02·r03). 같은 pair의 장애·대조 run, 그 안의 모든 서비스·window는 같은 fold |
| 대상 | 적격(data_valid, injection_valid, impact_confirmed) CPU 과부하·Pod 장애 case. 전체 69쌍을 서비스 원인 사례로 세지 않는다 |
| 지표 | AC@1, AC@3, Avg@5, MRR, 평가 case 수 |
| 불확실성 | case 단위 짝지은 bootstrap 95% (2000회, seed 0). window 단위 금지 |
| **주 비교** | **D vs A, Avg@5** |
| 보조 비교 | D vs A′ (단순 로그 정보 대비 의미 거리 추가 효과), D vs B (표현 차이), D vs C (서비스별 기준 효과) |
| 판정 | 짝지은 bootstrap 신뢰구간이 0을 포함하지 않을 때만 "낫다/나쁘다". 보조 비교는 서술 결과로 보고 |
| 탐지 | 이 실험은 원인 순위만 본다. 탐지 모델(LightGBM)은 고정 그대로. 로그 특징의 탐지 효과는 별도 실험으로 하며, 탐지가 좋아진 것을 원인 순위 개선으로 주장하지 않는다 |

**case 수 주의:** 평가 대상은 약 20~24 case로 예상된다. 한 case가 바뀌면 AC@1이 약 4~5%p 움직이므로 "차이 없음"이 나올 가능성이 높다는 것을 미리 적어 둔다.

## 9. 군집화의 위치

- 임베딩 군집(HDBSCAN 또는 KMeans)은 **대시보드 근거 표시와 시각화**에만 쓴다. A~D의 입력 특징으로 쓰지 않는다.
- 군집을 CPU·Pod 같은 장애 유형이라고 부르지 않는다.

## 10. 바꾸면 어떻게 보고하는가
