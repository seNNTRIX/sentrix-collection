# Method B 대조 run 오경보 26건 분석 (사후·보조)

결과를 본 뒤 한 **사후·보조 분석**이다. 보고한 Method B 수치(대조 run 오경보율 37.7% = 26/69), 모델, 문턱, 규칙은 바꾸지 않는다.
`analyze.py`가 Method B fold 탐지기를 그대로 다시 학습했고, fold 문턱 3개와 run 123개의 경보 여부가 기록(`experiments/20261123-linux-v1-eval-b/results.json`)과 완전히 같았다.

## 1. 어떤 대조 run이 경보됐나

| 나눈 기준 | 결과 | 해석 |
|---|---|---|
| 짝이 된 장애 종류 | CPU 6/15, 지연 6/15, 손실 6/15, Pod 4/15, 급증 4/9 | 몰림 없음 (Pod vs 나머지 Fisher p = 0.38) |
| 반복 회차 | 1회차 9/23, 2회차 6/23, 3회차 11/23 | 뚜렷한 차이 없음 |
| 시간대 (00~07시 vs 나머지) | 밤 5/16 | 차이 없음 (p = 0.77) |
| **수집 날짜 (KST)** | **10-27~10-29: 21/44 (48%)**, 그 외 날짜: 5/25 (20%). 10-23·24·26은 0/9 | 날짜에 몰림 (p = 0.038). 단 날짜로 나누는 기준을 결과를 본 뒤 골라서 탐색적 결과 |
| 경보 시점 | 가짜 장애 시작 후 100~290초, 중앙값 145초 | 특정 시점에 몰리지 않음 |
| 가짜 장애 구간 밖 | 경보된 run은 장애 전 정상 구간에서도 문턱 초과 비율 16.7% (안 된 run 8.5%), 회복 구간 14.7% (2.3%) | **run 전체가 평소보다 시끄러운 상태**였음. 가짜 장애 구간만의 현상이 아님 |

## 2. 어떤 피처가 점수를 올렸나 (LightGBM TreeSHAP, log-odds)

오경보 구간(대조 run 가짜 장애 구간 중 문턱 초과 214개)과 조용한 구간(문턱 이하 1,238개)의 평균 기여도 차이:

| 순위 | 피처 | 기여도 차이 | 원래 값 (오경보 / 조용 / 진짜 장애) |
|---|---|---|---|
| 1 | f_ct_in_p50_lr__max (들어오는 호출 p50의 평소 대비 비율, 최대) | +0.85 | 0.058 / 0.019 / 1.065 |
| 2 | f_cm_cpu_limit_ratio_mean__mean (CPU 한도 대비 사용률 **절대값**, 평균) | +0.82 | 0.056 / 0.054 / 0.097 |
| 3 | f_ct_out_p90_lr__mean (나가는 호출 p90 비율, 평균) | +0.52 | 0.232 / 0.071 / 1.266 |
| 4 | f_cm_mem_limit_ratio_mean__max (메모리 한도 대비 사용률 **절대값**, 최대) | +0.50 | 0.435 / 0.415 / 0.410 |
| 5 | f_cm_cpu_limit_ratio_mean__max | +0.40 | 0.300 / 0.291 / 0.539 |

출처별 합: 지표 +2.80, trace +1.86, 이웃 +0.76, 로그 +0.01.
각 오경보 run의 첫 경보 구간에서 가장 크게 기여한 피처: 메모리 절대값 계열 17/26, 나가는 호출 p90 5/26.

진짜 장애 구간에서는 trace 피처가 주도한다(p50 비율 최대 +2.68, 호출 오류율 +1.69, 경로 p90 +1.40).

## 3. 해석 (확인하지 않은 추정 포함)

- 오경보는 장애 종류·회차·시간대가 아니라 **수집 날짜(10-27~29)와 run 단위 상태**에 몰렸다. 그 기간의 클러스터 상태(어느 PC에서 수집했는지, 재시작 여부, 리소스 상태)를 수집 기록과 대조해야 원인을 말할 수 있다. 아직 확인하지 않았다.
- 오경보를 올린 피처에는 **평소 대비 변화가 아닌 절대값 피처**(CPU·메모리 한도 대비 사용률 평균)가 크게 들어 있다. 이런 값은 환경과 날짜에 따라 기준 자체가 바뀌어서, 학습 환경과 다르면 오경보를 만들기 쉽다. 다만 run 단위 메모리 중앙값은 경보 run과 아닌 run이 비슷해서(0.413 vs 0.417), 절대값 하나만으로 설명되지는 않고 trace 지연 비율과 함께 작용한 것으로 보인다.
- 지연 비율 피처도 오경보 구간에서 조용한 구간보다 높지만(p50 비율 0.058 vs 0.019), 진짜 장애(1.065)보다 훨씬 작다. 작은 지연 흔들림이 절대값 피처와 합쳐져 문턱을 넘은 것으로 보인다.

## 4. 다음에 할 수 있는 것 (사전등록 후)

- 탐지기에서 절대값 피처를 뺀 변형(예: 변화량 피처만)을 같은 B 방식으로 평가해 오경보율과 탐지율을 비교. 결과를 본 뒤 정한 변경이므로 계획을 먼저 등록하고, 주 결과와 섞지 않는다.
- 10-27~29 수집 기록(수집 PC, 클러스터 재시작, 노드 리소스) 확인.
