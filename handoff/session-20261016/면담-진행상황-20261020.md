# SentriX 진행 상황 (10/20 면담)

> 데이터 수집 환경 구축과 장애 주입 검증까지 끝났고, 시험 수집에서 네트워크 장애가 실제 서비스 호출에 걸리지 않는 문제를 찾아 주입 방식을 고치는 중입니다.

---

## 1. 수집 환경 변경

대상 시스템은 그대로 Online Boutique이고, 수집 환경을 Windows에서 학교 실습실 Linux PC로 옮겼습니다.

| | 이전 | 현재 |
|---|---|---|
| 환경 | Windows + Docker Desktop (노트북) | 학교 실습실 Linux PC + k3s |
| 확보한 데이터 | 장애 3건 + 대조 3건 (CPU, Pod 장애, 트래픽 급증) | 장애 69건 + 대조 69건 목표 |
| 네트워크 지연·손실 | 확보 못 함 | 포함 |

옮긴 이유

- Windows 환경에서는 네트워크 지연·손실 장애를 서비스 간 연결 단위로 넣고 검증하기 어려웠습니다.
- 노트북 메모리가 빠듯해 모니터링 도구가 자주 죽었고, 노트북을 켜 둬야 해서 장시간 수집이 어려웠습니다.
- 공개 데이터 RE2-OB도 Online Boutique라서, 같은 앱으로 계속 수집하면 서비스 이름·호출 구조·계측 방식이 같아 두 데이터를 함께 쓰기 쉽습니다.
- 기존 Windows 데이터 6건은 버리지 않고 따로 보관하되, 새 데이터와 섞지는 않습니다.

---

## 2. 수집 설계

장애를 넣는 run과, 같은 조건에서 장애만 없는 대조 run을 한 쌍(pair)으로 수집합니다.

| 장애 종류 | 원인 위치 | 대상 | 반복 | 건수 |
|---|---|---|---|---|
| CPU 포화 | 서비스 | checkout, productcatalog, currency, recommendation, payment | 3 | 15 |
| Pod 장애 | 서비스 | 위 5개 | 3 | 15 |
| 네트워크 지연 | 서비스 간 연결 | frontend→productcatalog 등 5개 연결 | 3 | 15 |
| 패킷 손실 | 서비스 간 연결 | 위 5개 연결 | 3 | 15 |
| 트래픽 급증 | 입구(frontend) | 부하 3단계 | 3 | 9 |
| 합계 | | | | 69쌍 (138 run) |

- run 하나는 25분입니다. 정상 구간 → 장애 5분 → 회복 구간 순서이고, 장애 시작 시점은 7~12분 사이로 매번 다르게 둡니다.
- 사용자 트래픽은 k6로 "홈 → 상품 → 장바구니 → 결제" 흐름을 계속 보냅니다.
- 평가는 반복 번호 기준 3-fold로 나눕니다. 같은 장애에서 나온 구간이 학습과 테스트에 동시에 들어가지 않게 하려는 목적입니다.
- 원인 위치는 서비스 이름을 분류하는 방식이 아니라, 모든 서비스와 연결에 점수를 매겨 순위를 내는 방식으로 할 예정입니다.

## 4. 시험 수집 결과

| 장애 | 장애 주입 | 사용자 영향 |
|---|---|---|
| Pod 장애 (checkout) | 정상 | 있음. 장애 동안 결제 성공률 0% |
| CPU 포화 (checkout) | 정상 (CPU 사용량·throttling 증가) | 없음 |
| 네트워크 지연 (frontend→productcatalog) | 실제 서비스 호출에는 안 걸림 | 없음 |
| 패킷 손실 (frontend→productcatalog) | 실제 서비스 호출에는 안 걸림 | 없음 |

### 네트워크 장애가 안 걸린 이유

검증 단계에서는 Pod IP로 직접 ping을 보내 확인했고, 그때는 지연이 정상적으로 걸렸습니다. 그런데 실제 서비스들은 서로를 Service 주소(ClusterIP)로 호출합니다.

```
검증 때     probe Pod ──(목적지: 상대 Pod IP)──▶ 지연 걸림
실제 서비스  frontend ──(목적지: ClusterIP)──▶ 노드에서 Pod IP로 변환 ──▶ productcatalog
                       ↑ 이 시점에는 목적지가 ClusterIP라 Chaos Mesh 필터에 안 걸림
```

Chaos Mesh는 "목적지가 상대 Pod IP인 패킷"에만 지연을 거는데, 패킷이 출발할 때는 목적지가 아직 ClusterIP라서 필터를 그냥 지나갑니다. 검증 방식이 실제 호출 경로를 대표하지 못한 것이 원인입니다.

정식 수집 전에 찾아서, 지연·손실 30쌍(약 48시간)을 효과 없는 데이터로 모으는 일은 피했습니다.

### CPU 장애에 영향이 없던 이유

checkout은 거래 하나에 한 번만 호출되어서, 조금 느려져도 전체 응답 시간에 거의 드러나지 않았습니다. 스트레스 프로세스 수를 1개에서 4개로 늘려, 앱이 쓸 수 있는 CPU 몫을 더 줄이는 방향으로 다시 시험합니다.

### 트래픽 급증 단계

처리 용량 측정 결과로 보면 기존 단계(초당 3.6 / 4.8 / 6.0건)는 대부분 사용자 영향이 나지 않습니다. 초당 4.8 / 6.0 / 8.0건으로 올리는 것을 검토하고 있습니다. 가장 낮은 단계는 "부하는 늘었지만 장애는 아닌 경우"로 남겨 오탐 분석에 쓰려고 합니다.

### 그 외 해결한 문제

- 실습 PC 점검 스크립트의 오판정 3건 (접속 실패를 정상으로 판정 등)
- k3s 내장 kubectl 권한 문제
- 학교망에서 GitHub 파일 다운로드가 수 분씩 걸려 설치가 실패 → 미리 받아 두고 설치하도록 변경
- Pod 장애 검증 스크립트 버그, 대조 run 매칭 버그
- 부팅 직후 시계 오류에 대비해, 시간 동기화가 안 되어 있으면 수집을 시작하지 않도록 함

---

## 5. 지금 하고 있는 것

1. 검증 단계를 실제 호출 경로(Service 주소)까지 확인하도록 확장
2. 네트워크 장애 주입 방식 두 가지를 비교해 하나로 확정
   - Service 주소(ClusterIP)를 지연 대상에 추가하는 방식
   - 받는 쪽 Pod에서 돌아가는 응답 패킷에 지연을 거는 방식
3. 장애 템플릿 수정 후 시험 수집 2차: 지연, 손실, CPU(스트레스 4개)
4. 결과로 장애 강도를 확정하고 정식 수집 시작

## 6. 앞으로 일정 (11/20 전시회 기준)

남은 기간이 한 달이라 일정을 다시 짰습니다. 핵심은 두 가지입니다.

- **수집을 밤에도 계속 돌립니다.** 하루 8~10시간씩만 돌리면 69쌍에 3주 넘게 걸려 전시회를 맞출 수 없습니다. 밤낮없이 돌리면 순수 110시간이라 재시도를 포함해 약 9~10일이면 끝납니다.
- **수집하는 동안 나머지를 동시에 진행합니다.** 모델은 RE2-OB로 먼저 개발하고, 백엔드·모델 서버·대시보드는 지금 떠 있는 실습 PC 환경을 대상으로 미리 만듭니다.

| 기간 | 수집 (실습 PC) | 모델 | 백엔드·대시보드 |
|---|---|---|---|
| 10/20~10/22 | 네트워크 장애 수정, 시험 수집 2차, 강도 확정 | RE2-OB 다운로드, 데이터 구조 확인 | 저장소 구성, API 초안 |
| 10/23~11/1 | 정식 수집 (밤샘 운영) CPU·지연·손실 45쌍 → Pod 장애 15쌍 → 트래픽 급증 9쌍 | RE2-OB로 feature 설계, 기준 모델, 평가 코드 | 실시간 지표 조회, 모델 서버 틀(가짜 모델), 대시보드 화면(가짜 데이터) |

**전시회 데모 방식**

- 전시장이 같은 학교라서, 전시장 노트북 브라우저에서 학교 내부망으로 실습 PC의 대시보드에 접속하는 방식으로 진행합니다. 장애 주입부터 원인 후보 표시까지 실습 PC에서 실시간으로 돌아갑니다.
- 전시장 네트워크에서 실습 PC 주소로 접속이 되는지는 미리 시험해 둡니다(실습실과 전시장이 같은 내부망인지, 방화벽에 막히지 않는지).
- 당일 실습 PC가 재부팅되거나 네트워크가 끊길 경우를 대비해, 수집한 장애 사례를 다시 재생해서 보여주는 방식도 예비로 준비합니다.

## 7. 여쭤보고 싶은 것

- **실습 PC를 11월 초까지 밤에도 켜 두고 수집해도 될지** (재부팅·자동 업데이트·Windows 부팅 자제 요청 포함). 이게 안 되면 수집 규모를 45쌍으로 줄여야 합니다.

- 직접 수집 69건과 RE2-OB 90건으로 평가하는 구성이 충분한지
